3.2 Aggregators → Odoo POS: mn_food_aggregator_pos (Moaz Nabil)

  • v17/18/19, $1,000 one-time, OPL-1, 2,111 LOC, zero reviews, solo KSA developer.
  • Delivers: per-platform webhook endpoint, HMAC-SHA256 verification, idempotency, store→POS & SKU (AR/EN) mapping, auto-accept rules, full order state machine with outbound status push, reject-with-reason, driver info, rush-hour pause, cashier floating panel (6 s polling + sound), CSV settlement reconciliation with balanced commission journal entries, GMV/commission/net dashboard, ZATCA e-invoice on close, two security groups, sandbox flag, 60-day log purge.
  • Auth: API key + secret (Jahez), OAuth 2.0 (HungerStation/Delivery Hero), partner creds (Keeta), signed webhook.
  • Limits: generic framework (field names mapped at install, not validated adapters); status-push URLs unspecified; no outbound menu publishing; Marsool unconfirmed; "Odoo Online" claim is really Odoo.sh/on-prem; OPL-1 = one licence per client, cannot be bundled into a CodeOx product.
  • API access (from listing): Jahez — integration@jahez.net; HungerStation — Partner/POS API via account manager (developer.hungerstation.com); Keeta — merchant.mykeeta.com / developers.mykeeta.com; Marsool — merchant support, no public portal.
  • Verdict: buy one licence for pilot (saves 4–6 weeks); within 2 weeks decide keep or re-implement as cdx_pos_aggregator under CodeOx licence.

3.3 KSA payment / terminal modules for Odoo

  • Gateways: Moyasar (SAR/Mada/Apple Pay), Tap, HyperPay, PayTabs — Apps Store, ~SAR 50–1,500/app/yr; verify 19.0 builds.
  • Terminals: Geidea / NearPay / Verifone ECR via IoT Box or TCP/HTTP — custom or third-party.
  • Mada = >90 % of KSA cards, >95 % of card transactions; Stripe unusable for KSA-resident merchants.

5 · Unified Delivery-Aggregator Hub

Urban Eats' explicit ask: one system to run every delivery platform — HungerStation, Keeta, Noon Food, Jahez, Marsool, ToYou — instead of a counter full of tablets. This is the single strongest wedge for Odoo, and it is fully deliverable.

5.1 The problem today

  • Tablet chaos: one tablet/portal per aggregator → staff juggle 4–6 devices, miss orders at peak.
  • Manual re-keying: delivery orders typed back into the POS → errors, slow tickets, no clean audit trail.
  • Menu & price drift: every platform maintained separately → mismatched items, wrong prices, stale availability.
  • Stock oversell: no shared inventory → sold-out items still live on aggregators (no auto "86").
  • No true delivery margin: commissions and settlements live in each platform's own reports, never consolidated.

5.3 Two build routes

Route A · Direct adapters (own it)

  • Build cdx_pos_aggregator under CodeOx licence — one adapter per platform
  • No recurring middleware fee; full control; productisable across future F&B clients
  • Needs API / POS-partner access from each aggregator (external onboarding)
  • Start from the mn_food_aggregator_pos framework to save 4–6 weeks on the pilot

Route B · Middleware (fastest to pilot)

  • ›Connect once to Deliverect / FeedUs / Urbanpiper — they already hold certified adapters to all KSA platforms
  • ›Live in weeks, minimal per-platform onboarding
  • ›Recurring per-platform SaaS fee; less control over data
  • ›Good bridge: start on middleware, bring high-volume platforms in-house later

Recommendation: middleware (Route B) for a fast pilot on the top 2 platforms, then migrate high-volume platforms to direct adapters (Route A) as the CodeOx F&B product matures.

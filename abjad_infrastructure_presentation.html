You gave us access to your AWS account so we can deploy the new Abjad teacher‑hiring platform.

Capacity Check

The Server Is Already Fully Used

We measured the live server. The existing application is using nearly everything the server has — there's no room left over.

Memory in useonly ~160 MB of 4 GB free
"Swap" overflow in use~1.6 GB — already borrowing slow disk space when memory runs out
  • The server also runs an older software version (Node.js) than the new platform needs.
  • And it has no MongoDB database — which the new platform requires.
The Decision

Why Not Deploy on the Same Server

  • Protects what's live.Your existing application keeps running exactly as it is — zero risk of disruption.
  • No spare capacity.With memory already full, adding three more applications would slow everything down.
  • Different software needs.The new platform needs a newer Node.js and MongoDB — changing these in place would put the existing app at risk.
  • Designed for its own home.The new platform was built for separate, managed infrastructure from the start.
Our Recommendation

A Second, Dedicated Server

A new server just for the teacher‑hiring platform — completely separate from what's running today. Fully isolated: no shared risk in either direction.

2× memory2 CPU cores, 8 GB memory (t3a.large) — double today's server
1,000 userssized for up to 1,000 concurrent users at launch, with room to grow
Fresh installcurrent Node.js version, clean environment, no conflicts
Managed DBMongoDB Atlas — automatic backups, doesn't consume server memory

Good to Know

Routine Housekeeping, While We're At It

A few standard hardening steps every setup adds as it matures — nothing urgent, and none of it blocks the deployment.

  • Restrict remote server access to trusted locations only.
  • Set up individual logins with two‑factor authentication, instead of one shared account.
  • Enable storage encryption and automated backups.
  • Add basic uptime and performance alerts, so issues are caught automatically.

04 · Integration Readiness

Integration Pre-Conditions & Client Responsibilities

The following are pre-conditions for delivery. The client (TAHAKOM, directly or via the main contractor) is expected to ensure these are in place. Where systems are not integration-ready, the affected integration is treated as a change request and re-scoped separately.

Bafar Labs operates on the assumption that target systems are integration-ready

  1. All integration target systems must be integration-ready, meaning documented and stable APIs exist (REST, SOAP, OData, IDoc, or vendor-specific equivalents), API credentials and sandbox environments are provided in advance of integration sprints, vendor support is engaged where third-party SaaS systems are involved, and no fundamental modifications to legacy systems are required from Bafar Labs.
  2. The client provides and supports during integration: ERP, HR, identity (Microsoft Entra / Azure AD or equivalent), and any other target system endpoints; designated single point of contact per target system; reasonable response times from system owners during integration sprints; test data and UAT environment access.
  3. Where client systems are not integration-ready (no API, undocumented, legacy without vendor support), the affected integration becomes a change request and is re-scoped separately. Bafar Labs does not modify, upgrade, or rebuild client legacy systems within this scope.
  4. Hosting infrastructure: the client provides production-grade hosting (cloud or on-prem) per agreed sizing specification. Bafar Labs supplies the application stack, container images and deployment automation.
  5. Network access: the client provides network connectivity, VPN access and firewall rules required for development, deployment and ongoing operations.
  6. Master data: the client provides clean, validated master data (vehicle list, driver list, employee list, spare parts master, BOM, workshop list, etc.) at the agreed migration cut-off point.
  7. Hardware availability: all hardware items listed as common exclusions are available, installed, configured and operational before the corresponding software module integration begins.

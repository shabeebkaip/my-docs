Internal Requirements Spec · In-Vehicle Edge Deployment

Intelligence on every bus. Nothing leaves the vehicle until it has to.

A self-contained Vision AI node on each bus analyses 8 CCTV streams in real time, detects safety and security events on-board with no internet dependency, and alerts the driver instantly. When a connection is available, events, clips and analytics sync to a central fleet server and the wider team is looped in. This document defines the full platform infrastructure we need end to end, what runs where, our own delivery challenges, and exactly what we need to get started.

01 / What we are building

One self-contained intelligence unit per bus, one server behind them all.

This is a mobile, in-vehicle edge deployment, not fixed-site analytics run from a data centre. The bus moves, loses signal in tunnels and remote routes, and sits in cabin heat. So every time-critical decision happens on-board. A central server sits behind the fleet to receive events, store evidence, run the dashboard and route notifications to the team when buses are connected.

On-Bus Compute

A rugged in-vehicle AI computer per bus, wired to the 8 cabin and door cameras. Decodes every stream, runs all analytics locally, buffers events and clips. No feed needs to leave the bus to be understood.

Real-Time Detection

Nine scenarios, from a sleeping driver to a weapon in frame, detected on-board in real time. Because detection runs locally, a dead zone never blinds the system.

Alerting

Offline, the node alerts the driver directly in the cabin. Once a connection exists, escalations route to the team through AIWA chat and AIKA voice.

Store-and-Forward Sync

Events, metadata and evidence clips are written locally first, then synced to the central server when a link returns. Nothing is lost during offline stretches.

Central Server & Storage

An off-vehicle server stores all events, clips and (optionally) full-journey recordings, runs the fleet dashboard and analytics, and manages notification routing across the fleet.

Privacy by Design

Detection runs on pose, object geometry and behaviour, not stored facial identity. Only flagged clips are retained and synced by default, which keeps the system defensible and bandwidth low.

04 / Central server & storage · what we need

The server behind the fleet, and the storage question.

Yes, we need an off-vehicle server. It receives everything the buses sync, stores it, runs the dashboard and analytics, and routes notifications. How big the storage needs to be depends entirely on one decision: do we keep only event clips, or full journey recordings.

4.1 · What the central server does

Ingest

Receives events, metadata and clips synced from every connected bus, deduplicated and ordered.

Store

Keeps event history, evidence clips, and optionally full-journey video, on tiered storage.

Serve

Runs the fleet dashboard, clip playback, search and analytics for operators and supervisors.

Route

Decides who is notified for which event class and pushes to AIWA and AIKA.

Train

Central GPU capacity to retrain and improve models on real footage, then push updates to the fleet.

Secure

Access control, encryption, and retention policy so stored footage stays compliant.

4.2 · The storage reality (this is the big sizing decision)

Two very different storage worlds, and the client needs to choose which one they want. The gap between them is enormous at fleet scale.

Events + clips only (default)
  • Only short clips around each detected event are stored
  • Roughly megabytes per bus per day, driven by how many events fire
  • Across the whole fleet this stays modest and cheap to hold
  • This is what we recommend as the default
Full-journey recording (optional)
  • Every camera recorded continuously for the whole route
  • 8 cameras at 1080p H.265 is on the order of 15 to 20 GB per bus per day
  • Across 14,000+ buses that becomes multiple petabytes per month
  • Needs a large tiered storage back end and a clear retention window

If the client wants full traveling clips, storage grows fast. The event-clips default is small. Continuous full-journey recording for 14,000+ buses is a multi-petabyte problem that needs a proper storage design: keep footage on the bus and only pull on request, or sync everything and hold it centrally on tiered storage (fast disk for recent, cheaper bulk for archive) with a defined retention window. We need the client to tell us which model they want, because it changes the storage sizing by orders of magnitude. Practical middle ground: keep full journeys on the bus for a short rolling window, sync only event clips by default, and pull a full journey centrally only when an incident needs it.

4.3 · Server sizing follows the fleet

For the MVP we can simply spin up a modest cloud server instance to receive the one bus, hold its clips and run the dashboard. That is fast to stand up and needs no hardware procurement. As buses are enrolled and, especially, if full-journey recording is turned on, storage and load grow. The straightforward first move is to vertically scale that instance (more CPU, RAM, GPU and storage), but bigger instances cost more, and storage cost climbs with retention. Past a point, scaling out horizontally with tiered storage becomes the cheaper path than one ever-larger server. The growth path is covered in the scaling section next, and training capacity is planned separately from the always-on ingest and dashboard workload.

06 / How alerting behaves

Offline, we alert the driver. Online, we loop in the team.

This is the exact behaviour you described, made explicit. The system always does something useful, even with zero signal.

No connection (on route)
  • Detection keeps running fully on the bus
  • Driver is alerted directly in the cabin (buzzer / indicator) for driver-facing events
  • All events and clips are stored locally, queued for later
  • Nothing is lost, nothing waits on a server
Connected (cellular or depot)
  • Queued events and clips sync to the central server
  • Escalations route to the team through AIWA and AIKA
  • Supervisors and dispatch see events on the dashboard
  • The driver alert has already happened locally; this adds the team layer

The key promise: the driver is never left un-alerted just because the bus has no signal. Team notification is an escalation layer on top, activated by connectivity, not a dependency for the core safety alert.

07 / Scaling from 1 to 14,000+

The bus side scales by replication. The server side scales up, then out.

Two different scaling stories, because the two sides grow differently.

On-bus: horizontal by nature

Every bus is an identical, independent node. Adding buses does not add load to any shared component, it just adds more self-contained units. Bus 14,000 runs the same image as bus 1. This is the easy half.

Central: vertical first, then horizontal

The central server starts small for the MVP. As buses enrol, we scale it up (more CPU, RAM, GPU and storage on a bigger server) until a single machine is no longer sensible, then scale out horizontally (multiple servers behind a load balancer, sharded storage, separate ingest and dashboard tiers). Storage in particular scales independently and tiered.

Where the central load actually comes from. Not per-frame video, that stays on the bus. The central load is event ingest, clip storage, dashboard queries, notification fan-out and model training. Ingest and storage grow linearly with the number of active buses and the retention policy. Training is bursty and planned separately so it never competes with always-on ingest. This is why the storage decision in section 4 matters so much: full-journey recording is what turns a manageable central footprint into a heavy one.

8.1 · What this layer needs

Training GPUs

Training-class GPU capacity on our side to train and fine-tune the models. This is heavier, separate hardware from the inference GPU on the bus. The bus box runs finished models; this builds them.

Model Registry

Versioned storage of every model, so we always know what is deployed where, and can pin or roll back a specific version.

Fleet Control Plane

A management layer to see which buses are online, which model version each runs, and their health, and to push updates and config out to them remotely.

OTA Update Pipeline

Safe over-the-air model and software updates with staged rollout (a few buses first, then wider) and instant rollback if a new model misbehaves.

Model Monitoring

Tracking confidence, false positives and drift per scenario in the field, so we know when a model is degrading and needs retraining, closing the loop back to step 1.

Two different GPUs, two different jobs. The GPU on the bus does live inference and is covered in section 3. The GPU capacity here does training and is on our side. They are not the same hardware and not interchangeable, which is why training capacity is planned separately from the always-on runtime.

Indicative, not final. The exact tooling for training, registry and OTA is chosen as we finalise the architecture. What matters here is that these capabilities are part of what we run, and are accounted for from the start rather than discovered later.

09 / Our delivery challenges

What is hard on our side, stated honestly.

Named up front so we plan for them, not discover them mid-project.

Models need real training

Out-of-box models will not be accurate enough on these specific camera angles, lighting and cabin layouts. We need to train and tune on real footage from these buses. That takes annotated data, iteration, and central GPU capacity for training runs, which is a real cost and time investment before accuracy is where it should be.

Rare events are hard to validate

Weapons, fights and falls may not occur naturally in a short window. We validate these with controlled staged tests and, where needed, synthetic and augmented training data, so we can prove detection without waiting on a real incident.

False positives take tuning

Fresh models over-alert. Getting from noisy to trustworthy takes a tuning cycle per scenario. Day-one numbers are not final numbers, and we report precision and recall honestly rather than one inflated accuracy figure.

The environment is unforgiving

Cabin heat, vibration, dirty power and intermittent connectivity all have to be handled for the system to run reliably for weeks unattended. We design for it, but it is genuinely harder than a fixed-site install.

10 / What we need to start

The checklist to start.

Blocking items must be answered before we can order hardware or install.

Ask 01 Camera & MDVR details Blocking

Make/model of the installed cameras and NVR/MDVR on the target bus, and how streams are exposed (RTSP, ONVIF, or MDVR export). Decides the camera-input variant of the edge box and whether we need any adapters.

Ask 02 Target bus + route access Blocking

One nominated in-service bus, its typical route, and depot access to install and check. The route helps us anticipate dead zones for the sync behaviour.

Ask 03 Power tap & install slot Blocking

A switched vehicle power tap point and a booked install window to mount the box, wire power, connect the camera network, and fit the driver alert indicator.

Ask 04 Storage preference

Whether the client wants event clips only (default) or full-journey recording, and for how long. This sizes the central storage. See section 4.

Ask 05 Camera positions

Which of the 8 cameras covers driver, doors, aisle and cabin. Drives which scenario runs on which feed.

Ask 06 Connectivity for sync

A data SIM (or approval to use ours) and depot Wi-Fi for the sync demonstration. The system runs offline regardless; this enables team escalation and central sync.

Ask 07 Alert recipients

Who receives which alert once online (supervisor for compliance, dispatch for safety-critical), so we wire AIWA / AIKA routing.

Ask 08 Sample footage

Any existing recorded clips from these buses to pre-train and tune models to the real angles and lighting before install. Directly improves accuracy in the live window.
